# FORGE Security Architecture & Limitations

## 1. Core Threat Model & Design Principles

FORGE is engineered as a local-first, peer-to-peer (P2P) engineering workspace. Its primary security posture is zero-knowledge persistence: **workspace documents, edits, and file trees never reside on or traverse a centralized cloud database or document server.**

### Data Flow Breakdown
1. **Local State**: All document CRDT states reside in the browser's memory and are persisted locally into `IndexedDB` on the user's device.
2. **Peer-to-Peer Data Channels**: When two or more peers join the same workspace, synchronization messages (Yjs update deltas and awareness state) travel directly over WebRTC `RTCDataChannel` connections.
3. **Signaling Server**: The WebSocket signaling server facilitates initial WebRTC handshakes (exchanging SDP offer/answer session descriptors and ICE candidate network routes). **No document contents or keystrokes are ever sent to the signaling server.**

---

## 2. Room IDs as Identifiers, NOT Authentication Credentials

> [!WARNING]
> Room IDs (e.g., `forge-atlas-7842`) function as **rendezvous identifiers**, not authenticated access tokens.

- Any peer possessing the room ID can connect to the signaling topic and attempt to establish a WebRTC data channel with other peers in that room.
- While room IDs generated by FORGE use sufficiently high-entropy random identifiers to avoid accidental collisions, guessing or sharing the room ID grants participation in the workspace.
- **Current Limitation**: FORGE MVP does not implement cryptographic user identity certificates, PKI, or password-based workspace access gates.
- Do not share room links across untrusted public channels if the workspace contains sensitive technical data.

---

## 3. End-to-End Encryption & Key Management Clarification

- WebRTC `RTCDataChannel` connections are automatically encrypted in transit using **DTLS (Datagram Transport Layer Security)** as mandated by the WebRTC W3C specification. This protects traffic against passive wiretapping on the local network path between peers.
- **Cryptographic Boundary Notice**: FORGE MVP does **not** claim custom end-to-end payload encryption beyond the standard WebRTC DTLS transport security. Without application-level key derivation (such as Diffie-Hellman key exchange with authenticated pre-shared keys or passphrases derived from URL hash fragments), malicious or compromised signaling servers could theoretically stage a man-in-the-middle (MitM) attack by intercepting and substituting DTLS fingerprints during signaling exchange.
- A future release will evaluate client-side Yjs payload encryption using WebCrypto `AES-GCM-256` keys derived from URL `#key=...` fragments (which are never sent to HTTP servers).

---

## 4. NAT Traversal & Network Privacy Considerations

- **IP Address Exposure**: To discover a direct network route between peers, WebRTC exchanges ICE candidates containing local and public IP addresses (via STUN). All participants in a room will discover the public IP addresses of other participants.
- **NAT / Firewall Traversal**: FORGE uses public STUN servers (such as Google's STUN infrastructure) for NAT discovery. In symmetric NAT or restrictive corporate firewall environments, direct P2P connections cannot be established without a TURN relay server.
- Connection is **not guaranteed** across all network topologies. When P2P fails, FORGE notifies the user of connection state rather than masking network failures.

---

## 5. Client-Side Safety & Environment Variables

- No API keys or cloud credentials are required or embedded in client bundles.
- Frontend environment variables (`VITE_SIGNALING_SERVERS`, `VITE_STUN_SERVERS`) specify transport URLs only. Never commit or expose private secrets in frontend builds.
- Document contents are executed in sandboxed read-only contexts (e.g., Markdown preview sanitizes unescaped HTML scripts to prevent XSS).
